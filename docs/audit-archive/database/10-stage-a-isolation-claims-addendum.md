#### Adjudication of Specific Questions:
- **Does direct event injection create a trusted QA call binding?**  
  **NO.** If direct injection injects a synthetic event where `event.to` is not `TELNYX_QA_TRACKING_DID` (or if no cryptographic lease was pre-opened in `activeLeases`), `isQaIngress` is false. `matchedQaRunId` is `undefined`, and `bindCallToTestRun()` is **never invoked**. The call is persisted in PostgreSQL as an unbound call.
- **Does `validateDestinationOrThrow()` actually perform allowlist validation for the injected call?**  
  **NO.** In `dialNextBuyer`, `result.call` is passed to `validateDestinationOrThrow(dialNumber, result.call)`. In `isQaCall(result.call)`, because `callContext._trustedServerQaFlag` is undefined and `this.boundCalls.get(result.call.id)` is undefined, `isQaCall` returns **`false`**. Step 2 (`if (!this.isQaCall(callContext)) return;`) triggers an **immediate return (BYPASS)**. Allowlist validation is **never executed**.
- **Can an unbound event bypass the allowlist?**  
  **YES.** The allowlist check is completely bypassed because the guard assumes an unbound call is a production commercial call. The guard does **not** fail closed on direct event injection.
- **Does `FakeTelephonyProvider` prevent that bypass from reaching Telnyx call control?**  
  **YES.** Immediately following the guard bypass in `dialNextBuyer` (line 1025), CallFlow executes `await this.provider.dialBuyer(...)`. Because `TELEPHONY_PROVIDER` is overridden by `FakeTelephonyProvider` in the test module, the call control request delegates to `FakeTelephonyProvider.dialBuyer()`, which runs strictly in memory.
- **Verdict for Point 1:** **`PASS WITH CONDITIONS`**  
  *Condition:* The system's safety under direct event injection relies **100% on `FakeTelephonyProvider` downstream interception**, because `validateDestinationOrThrow` does not enforce allowlist checks on unbound synthetic events.

### Point 3 — Correct Test Harness Teardown & Lifecycle Hooks

#### Forensic Lifecycle Trace:
In NestJS, module and application lifecycle hooks operate under strict conventions:

| Lifecycle Trigger | `onModuleInit()` Executed? | `onModuleDestroy()` Executed? | Status of Background Timers |
|---|:---:|:---:|---|
| `Test.createTestingModule(...).compile()` | **NO** | **NO** | Timers are **NOT started**. |
| `await moduleRef.init()` | **YES** | **NO** (Until close) | Timers **start**. Requires `moduleRef.close()`. |
| `const app = moduleRef.createNestApplication(); await app.init();` | **YES** | **NO** (Until close) | Timers **start**. Requires `app.close()`. |

#### Services with Active Background Intervals:
1. **`ReservationRecoveryService` (`reservation-recovery.service.ts#L31`):** `setInterval(..., 5 * 60 * 1000)` started in `onModuleInit()`. Cleared in `onModuleDestroy()`.
2. **`WebhooksService` (`webhooks.service.ts#L23`):** `setInterval(..., 5000)` started in `onModuleInit()`. Cleared in `onModuleDestroy()`.

#### Adjudication of Specific Questions:
- **Which lifecycle hooks start interval timers?**  
  `onModuleInit()`. If a test harness merely executes `.compile()`, `onModuleInit()` is **never called**, and interval timers are never instantiated.
- **What is the correct cleanup method for the actual proposed harness?**  
  - If the Stage A harness uses `moduleRef = await Test.createTestingModule(...).compile()` without `app`:  
    If `await moduleRef.init()` is invoked, the correct teardown in `afterAll()` is:
    ```typescript
    afterAll(async () => {
      await moduleRef.close();
    });
    ```
  - If the harness compiles an application wrapper (`app = moduleRef.createNestApplication()`):  
    The correct teardown is:
    ```typescript
    afterAll(async () => {
      await app.close();
    });
    ```
- **Verdict for Point 3:** **`PASS`**  
  *Finding:* The proper teardown mechanism is verified. The harness must use `moduleRef.close()` when operating directly on `TestingModule`, avoiding invalid references to an uninstantiated `app` variable.

### Point 4 — Correction of SIP / ARI Isolation Claims

#### Forensic Verification of Assertions:
1. **Assertion: "No ARI originate operation is invoked by the direct Stage A event path."**  
   - **Supported by Source Code (`VERIFIED BY SOURCE CODE`):**  
     Exhaustive inspection of [`CallController.ts`](file:///C:/Projects/callflow-agent-a/apps/api/src/telephony/call-controller.ts) proves that `CallController` does not import, inject, or reference `AsteriskAriClientService`. Its outbound dialing delegates strictly to `this.provider.dialBuyer()`. When `this.provider` is `FakeTelephonyProvider`, no HTTP requests to port 8088 can be emitted by the direct event injection path.
2. **Assertion: "No Asterisk channel is originated by the FakeTelephonyProvider path."**  
   - **Supported by Source Code (`VERIFIED BY SOURCE CODE`):**  
     [`FakeTelephonyProvider.dialBuyer`](file:///C:/Projects/callflow-agent-a/apps/api/src/telephony/fake.provider.ts#L24-L42) records actions in an in-memory array (`this.actions.push(...)`) and returns a static string. It contains zero network sockets, zero HTTP clients, and zero Asterisk channel origination code.
3. **Assertion: "UDP port 5060 is completely dormant."**  
   - **Empirical Reality (`UNVERIFIED`):**  
     While source code proves that CallFlow's NestJS backend does not send SIP packets, Asterisk container `callflow-asterisk-qa` is running independently on the host. PJSIP endpoints configured with Telnyx credentials (`PJSIP/telnyx-caller`) emit periodic SIP OPTIONS (qualify) pings or registration refreshes over UDP 5060 depending on `pjsip.conf` timers (`qualify_frequency = 60`).
   - Claiming that the UDP 5060 socket has "zero network activity" without real-time packet capture (`tcpdump` / Wireshark) is an **unverified empirical overstatement**.
- **Verdict for Point 4:** **`PASS WITH CONDITIONS`**  
  *Condition:* Application-layer SIP and ARI isolation is verified by source code. Container-level UDP socket dormancy is explicitly classified as **`UNVERIFIED`** without active network packet capture telemetry.
