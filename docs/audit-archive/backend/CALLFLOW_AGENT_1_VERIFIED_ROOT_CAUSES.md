## 2. In-Depth Root Cause Analysis of Confirmed Defects

### `CB-FE-001`: Root Next.js Starter Page
- **Source File:** `apps/web/src/app/page.tsx`
- **Initial Symptom:** Visitors navigating to the root URL `/` saw the default Vercel/Next.js boilerplate ("Get started by editing src/app/page.tsx") rather than being directed into CallFlow.
- **Root Cause:** The default file generated by `create-next-app` was never replaced with application-level routing logic.
- **Architectural Impact:** Unauthenticated users were not prompted to log in, and authenticated users were not redirected to `/protected`, causing severe brand degradation and broken user onboarding.
- **Remediation:** Converted `apps/web/src/app/page.tsx` to an auth-aware server component utilizing Supabase `createClient()`. If a session exists, it issues a server-side redirect to `/protected`; otherwise, it redirects to `/login`.

---

### `CB-FE-002`: Invitation Middleware Token Context Loss
- **Source File:** `apps/web/src/utils/supabase/middleware.ts`
- **Initial Symptom:** Unauthenticated recipients clicking invitation links containing `?token=...` lost their token context upon being redirected.
- **Root Cause:** The Next.js Supabase middleware checked `if (!user && !isPublicRoute)` and redirected directly to `/login`, discarding the query string on invitation routes (`/protected/accept-invitation` and `/protected/invitations`).
- **Architectural Impact:** Invited workspace members who were not yet signed in could not accept invitations directly, forcing them to re-click the link or manually reconstruct the URL after login.
- **Remediation:** Updated middleware to inspect `request.nextUrl.pathname` and preserve the invitation token:
  ```typescript
  if (isInviteRoute && token) {
    const url = request.nextUrl.clone();
    url.pathname = '/invitations';
    url.searchParams.set('token', token);
    return NextResponse.redirect(url);
  }
  ```

### `CB-FE-003`: HeaderMetrics Coupling & Polling Cascading Failure
- **Source File:** `apps/web/src/components/header.tsx`
- **Initial Symptom:** In workspace roles where the user lacked billing permissions (e.g., VENDOR or BUYER participants receiving HTTP 403 Forbidden on `/billing/balance`), live call metrics ceased updating, and repeated unhandled promise rejections appeared in the console.
- **Root Cause:** Both `/calls/live-calls` and `/billing/balance` were requested inside a single `Promise.all([fetchLiveCalls(), fetchBalance()])`. When the billing endpoint rejected with 403, `Promise.all` rejected immediately, aborting the live calls state update.
- **Architectural Impact:** Frontline agents and vendors were left blind to active phone calls simply because their workspace role restricted access to financial balance figures.
- **Remediation:** Refactored polling logic to use `Promise.allSettled`. If `/billing/balance` rejects with 403 or network failure, it safely sets `balance = null` while preserving real-time `liveCalls` metric rendering.

---

### `CB-FE-004`: Payment Direction Enum Type Contract Mismatch
- **Source File:** `apps/web/src/lib/payments.ts`
- **Initial Symptom:** Discrepancy between frontend TypeScript type definitions and backend NestJS DTOs for payment instructions.
- **Root Cause:** The frontend definition defined `direction: 'COLLECTION' | 'PAYOUT'`, whereas the backend Prisma schema and NestJS service strictly enforce `'COLLECTION' | 'DISBURSEMENT'`.
- **Architectural Impact:** While disbursement instructions rendered, filtering or mutating payment instructions using the `'PAYOUT'` string failed API schema validations and broke contract tests.
- **Remediation:** Standardized `PaymentInstruction.direction` to `'COLLECTION' | 'DISBURSEMENT'` across `apps/web/src/lib/payments.ts` and updated payment component tests.

---

### `CB-FE-005`: Onboarding Workspace Context Drop
- **Source File:** `apps/web/src/app/onboarding/onboarding-client.tsx`
- **Initial Symptom:** Upon creating a new workspace during onboarding, the application redirected to `/` or generic `/protected` without active workspace context, forcing the user to select the workspace again.
- **Root Cause:** The response from `POST /workspaces` returned `{ id, name, ... }`, but `handleCreateWorkspace` in `onboarding-client.tsx` did not extract `data.id` or synchronize `sessionStorage.setItem('callflow.active_workspace_id', id)`.
- **Architectural Impact:** Poor first-run user experience (UX) and immediate 400/404 errors if downstream views expected a workspace query parameter.
- **Remediation:** Captured the created workspace ID from the JSON response, updated `sessionStorage`, and navigated directly to `/protected/reporting?workspace=${createdWorkspaceId}` followed by `router.refresh()`.

### `CB-FE-006`: Reporting Dashboard Infinite Re-Render Loop & Recording Playback Test Failures
- **Source Files:** `apps/web/src/app/protected/reporting/page.tsx` & `src/app/protected/reporting/reporting-recording-playback.test.tsx`
- **Initial Symptom:** Four integration tests in `reporting-recording-playback.test.tsx` failed with timeouts (`Unable to find a label with the text of: Call recording audio player`).
- **Root Cause:** In Next.js App Router, `useSearchParams()` produces a new object reference on every render cycle. `fetchReporting` in `ReportingDashboard` had `searchParams` in its `useCallback` dependency array, and inside `fetchReporting`, `setCampaigns(extracted)` was invoked unconditionally on every fetch. This triggered an infinite re-render loop that repeatedly mounted and unmounted child rows, resetting `InlineRecordingPlayer` internal state before audio playback could mount.
- **Architectural Impact:** High CPU load on client machines, UI flickering, and complete breakdown of recording playback integration tests.
- **Remediation:**
  1. Replaced `searchParams` object dependency with stable string primitive `searchParamsString = searchParams.toString()`.
  2. Implemented `hasNew` differential check in `setCampaigns` to prevent redundant React state dispatch when campaign list contents have not changed.

---

### `CB-FE-007`: Reporting Table Column LocalStorage Merge Defect
- **Source File:** `apps/web/src/app/protected/reporting/page.tsx`
- **Initial Symptom:** Stored column configurations in `localStorage` could corrupt table rendering or hide newly deployed standard columns.
- **Root Cause:** The restore logic directly assigned parsed JSON array to state without verifying schema or merging missing default columns. Furthermore, if corrupted JSON was present in `localStorage`, `JSON.parse` threw unhandled exceptions.
- **Architectural Impact:** Users with existing cached configurations never saw newly introduced reporting metrics (such as recording links or dispute indicators).
- **Remediation:** Wrapped `JSON.parse` defensively, validated that `parsed` is an array of objects with valid column IDs, and automatically appended any new default columns to the tail while preserving user-ordered preferences.

---

### `CB-FE-008`: API Error Response Parsing & Formatting
- **Source File:** `apps/web/src/lib/api.ts`
- **Initial Symptom:** Server validation error messages were displayed in the UI as raw JSON strings: `API error (400): {"statusCode":400,"message":["phoneNumber must be valid E.164"]}`.
- **Root Cause:** `apiFetch` in `apps/web/src/lib/api.ts` attached the raw response body text directly to the error message without attempting JSON parsing.
- **Architectural Impact:** Unfriendly, technical error messages exposed to end users, violating UI/UX quality standards.
- **Remediation:** Updated `apiFetch` to check if error response body is JSON containing a `message` property (string or string array), formatting it into a clean, human-readable error while preserving HTTP status codes for programmatic inspection (`error.status` and `error.statusCode`).

---

### `CB-FE-009`: Authenticated Visitor Redirection on Login/Signup
- **Source Files:** `apps/web/src/app/login/page.tsx` & `apps/web/src/app/signup/page.tsx`
- **Initial Symptom:** Logged-in users navigating to `/login` or `/signup` were shown blank credential forms rather than being redirected to their workspace.
- **Root Cause:** Neither server component checked `supabase.auth.getUser()` before rendering the authentication forms.
- **Architectural Impact:** Confusing user experience and potential duplicate session creation.
- **Remediation:** Added server-side auth inspection. Authenticated visitors are automatically redirected to `/protected` (or `/protected/accept-invitation?token=${token}` if an invitation token was provided). Implemented defensive optional chaining on `supabase?.auth?.getUser?.()` to guarantee compatibility across all test and production environments.

## 3. Rejected Finding Analysis

### `INV-FE-001`: Workspace Header Context Claim (`x-workspace-id`)
- **Initial Finding:** The initial audit claimed that the frontend failed to send the `x-workspace-id` HTTP header on all API requests.
- **Verification Against Backend Source Code:**
  - Inspected `apps/api/src/authorization/workspace-roles.guard.ts`:
    ```typescript
    const workspaceId = request.params.workspaceId || request.query.workspaceId || request.body.workspaceId;
    ```
  - Inspected `apps/api/src/auth/jwt.strategy.ts` and all controller method decorators across `apps/api/src/*`.
  - The backend NestJS API does **NOT** read or trust an `x-workspace-id` header for authorization or workspace tenancy. Instead, it strictly enforces multi-tenant boundary isolation through explicit route parameters (`/workspaces/:workspaceId/...`), verified query parameters, or validated DTO request bodies.
- **Verdict: REJECTED.** Injecting `x-workspace-id` on the client would be an unverified, redundant header that does not align with backend security architecture. Client-side workspace context must continue to flow through route parameters and query strings.

## 4. Concurrency Artifacts

### `SB-FE-001`: Buyers Page Test Timeout
- **Source File:** `apps/web/src/app/protected/buyers/page.test.tsx`
- **Observation:** When running all 44 test files concurrently, the Vitest test runner experienced severe CPU contention on Windows (total test suite execution: ~10 minutes across 328 tests), occasionally triggering Vitest's 5000ms default test timeout.
- **Verification:** Executed in isolation (`npm --prefix apps/web test src/app/protected/buyers/page.test.tsx`), all 7 tests in `buyers/page.test.tsx` passed in under 3.5 seconds.
- **Verdict:** Suspected bug dismissed. No code defect exists in the component.
