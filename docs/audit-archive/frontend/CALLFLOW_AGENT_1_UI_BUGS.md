### BUG-FE-001: Default Next.js Starter Template Exposed on Public Root URL (`/`)
* **Status:** CONFIRMED BUG
* **Severity:** P0 (Critical Security & Public Identity Exposure)
* **Page / Component:** Root Landing Page
* **File Path & Line Number:** `apps/web/src/app/page.tsx`, lines 1–69
* **Expected Behavior:** Visiting the root URL (`/` or `https://app.callflow.com/`) should evaluate user authentication. If the user is logged in, it should redirect to `/protected`. If the user is not logged in, it should redirect to `/login` or render a branded CallFlow product landing page.
* **Actual Behavior:** The page renders the default "Create Next App" template with Vercel deploy buttons, documentation links (`https://nextjs.org/docs`), and the text: *"To get started, edit the page.tsx file."*
* **Reproduction Steps:**
  1. Open a browser window.
  2. Navigate directly to `http://localhost:3001/`.
  3. Observe the Next.js starter boilerplate.
* **API Dependency:** None (Pure client/server route handler).
* **Root Cause:** The default file generated by Next.js `create-next-app` was never replaced with application-specific routing or a landing page component.
* **Suggested Fix:**
  ```tsx
  import { redirect } from 'next/navigation';
  import { createClient } from '@/utils/supabase/server';

  export default async function HomePage() {
    const supabase = await createClient();
    const { data: { user } } = await supabase.auth.getUser();
    if (user) {
      redirect('/protected');
    } else {
      redirect('/login');
    }
  }
  ```
* **Regression Test Required:** Integration test verifying that unauthenticated requests to `/` receive a 307/308 redirect to `/login`, and authenticated sessions receive a redirect to `/protected`.

### BUG-FE-002: Middleware Invitation Token Extraction and Public Path Desynchronization
* **Status:** CONFIRMED BUG
* **Severity:** P0 (Authentication Redirection Flaw)
* **Page / Component:** Edge Session Middleware
* **File Path & Line Number:** `apps/web/src/utils/supabase/middleware.ts`, lines 11–19, 62–70
* **Expected Behavior:** Unauthenticated users accessing invitation links must be seamlessly routed to signup/login while strictly retaining the `token` parameter. The middleware must recognize both `/protected/invitations` and `/protected/accept-invitation`.
* **Actual Behavior:** Lines 64–68 only inspect `request.nextUrl.pathname.startsWith('/protected/invitations')`. When a user visits `/protected/accept-invitation?token=XYZ` without a session (e.g. from an email link or external invite), the middleware falls into the `else` branch, resetting the target to `/login` without preserving the `/protected/accept-invitation` target or token in a standard `next` redirect query param.
* **Reproduction Steps:**
  1. In an incognito browser window, navigate to `http://localhost:3001/protected/accept-invitation?token=valid-token-123`.
  2. Middleware triggers unauthenticated redirect.
  3. The browser lands on `/login` without passing the invite token or next target.
* **API Dependency:** Supabase SSR session client.
* **Root Cause:** Incomplete path matcher in `middleware.ts`.
* **Suggested Fix:** Update the condition:
  ```ts
  if (!user && isProtectedRoute) {
    const url = request.nextUrl.clone()
    const token = request.nextUrl.searchParams.get('token')
    if (
      (request.nextUrl.pathname.startsWith('/protected/invitations') ||
       request.nextUrl.pathname.startsWith('/protected/accept-invitation')) &&
      token
    ) {
      url.pathname = '/invitations'
      url.searchParams.set('token', token)
      return NextResponse.redirect(url)
    }
    url.pathname = '/login'
    return NextResponse.redirect(url)
  }
  ```
* **Regression Test Required:** Vitest tests verifying unauthenticated redirects for both invitation route variations.

## 2. P1 — CORE FUNCTIONALITY BROKEN

### BUG-FE-003: `HeaderMetrics` Unisolated `Promise.all` Polling Breaks `liveCalls` Display on 403
* **Status:** CONFIRMED BUG
* **Severity:** P1 (Core Dashboard Monitoring Broken for Participants)
* **Page / Component:** Global Header (`HeaderMetrics`)
* **File Path & Line Number:** `apps/web/src/components/header.tsx`, lines 24–41
* **Expected Behavior:** `liveCalls` metric should continuously display active call volume regardless of whether the user possesses billing viewing permissions.
* **Actual Behavior:** `fetchMetrics` bundles live calls and wallet balance into a single `Promise.all`:
  ```tsx
  const [liveRes, balRes] = await Promise.all([
    apiFetch(`/workspaces/${workspaceId}/calls/live-calls`),
    apiFetch(`/workspaces/${workspaceId}/billing/balance`)
  ]);
  ```
  For `VENDOR`, `BUYER`, or regular `MEMBER` roles lacking `billing:read` or `wallet:read`, `/billing/balance` returns HTTP 403 Forbidden. This unhandled rejection causes the entire `Promise.all` to fail, preventing `setLiveCalls(liveRes.liveCalls)` from ever executing and resetting both metrics to `null` (`—`).
* **Reproduction Steps:**
  1. Log into a workspace as a `VENDOR` or `BUYER` user.
  2. Observe the top header.
  3. Both the phone live calls counter and wallet balance display `—`.
  4. Inspect the browser console; observe a 403 Forbidden error every 10 seconds.
* **API Dependency:** `GET /workspaces/:id/billing/balance` and `GET /workspaces/:id/calls/live-calls`.
* **Root Cause:** Coupling two independent domain endpoints into an atomic `Promise.all` without permission checks or fallback isolation.
* **Suggested Fix:**
  Use `Promise.allSettled` or separate fetch routines:
  ```tsx
  const [liveResult, balResult] = await Promise.allSettled([
    apiFetch(`/workspaces/${workspaceId}/calls/live-calls`),
    apiFetch(`/workspaces/${workspaceId}/billing/balance`)
  ]);
  if (liveResult.status === 'fulfilled') setLiveCalls(liveResult.value.liveCalls);
  if (balResult.status === 'fulfilled') setBalance(balResult.value.balance);
  ```
* **Regression Test Required:** Unit test in `header.test.tsx` simulating a 403 Forbidden on `/billing/balance` and confirming `liveCalls` renders its integer value accurately.

### BUG-FE-004: Payment Direction TypeScript Contract Typo (`PAYOUT` vs `DISBURSEMENT`)
* **Status:** CONFIRMED BUG
* **Severity:** P1 (TypeScript Type Safety & API Contract Drift)
* **Page / Component:** Payments Client Library
* **File Path & Line Number:** `apps/web/src/lib/payments.ts`, line 22
* **Expected Behavior:** Client types must exactly mirror backend DTO enums and UI values (`COLLECTION` and `DISBURSEMENT`).
* **Actual Behavior:** `PaymentInstruction` interface defines:
  ```ts
  direction: 'COLLECTION' | 'PAYOUT';
  ```
  However, `apps/web/src/app/protected/payments/page.tsx` (lines 374–375) and backend NestJS controllers enforce `'COLLECTION' | 'DISBURSEMENT'`. Any code utilizing `direction === 'PAYOUT'` creates dead logic branches.
* **Reproduction Steps:**
  1. Inspect `apps/web/src/lib/payments.ts` at line 22.
  2. Inspect `apps/web/src/app/protected/payments/page.tsx` at lines 374–375.
  3. Note that selecting "DISBURSEMENT" produces a type incompatibility warning when assigned to `PaymentInstruction.direction`.
* **API Dependency:** `GET /workspaces/:id/payments/instructions`.
* **Root Cause:** Legacy terminology (`PAYOUT`) was updated to `DISBURSEMENT` in backend settlement engines but remained uncorrected in `lib/payments.ts`.
* **Suggested Fix:** Change line 22 to `direction: 'COLLECTION' | 'DISBURSEMENT';`.
* **Regression Test Required:** TypeScript compile check (`tsc --noEmit`).

### BUG-FE-005: Onboarding Completion Fails to Update Active Workspace Session Cache
* **Status:** CONFIRMED BUG
* **Severity:** P1 (Onboarding Flow Desynchronization)
* **Page / Component:** Onboarding Client
* **File Path & Line Number:** `apps/web/src/app/onboarding/onboarding-client.tsx`, lines 42–47
* **Expected Behavior:** Upon creating the first workspace, the client should extract the newly created workspace ID from the response, store it in `sessionStorage ('callflow.active_workspace_id')`, and navigate directly to `/protected/reporting?workspace=${newWorkspaceId}`.
* **Actual Behavior:** The form executes `router.push('/protected')` without capturing `res.json()`. Because the URL lacks `?workspace=`, the application falls back to `WorkspaceValidator`, which triggers a secondary client-side redirect, occasionally rendering an empty state or infinite loading indicator.
* **Reproduction Steps:**
  1. Create a fresh account without existing workspaces.
  2. Complete the onboarding input ("Acme Telecom") and click "Create Workspace".
  3. Observe that the browser routes to `/protected`, then flashes `Loading workspace context...` before settling.
* **API Dependency:** `POST /workspaces`.
* **Root Cause:** Response payload containing `{ id: string, name: string }` is ignored.
* **Suggested Fix:**
  ```tsx
  const data = await res.json();
  if (typeof window !== 'undefined' && data?.id) {
    sessionStorage.setItem('callflow.active_workspace_id', data.id);
    router.push(`/protected/reporting?workspace=${data.id}`);
  } else {
    router.push('/protected');
  }
  ```
* **Regression Test Required:** E2E / integration test for first-time workspace creation and immediate context redirection.

### BUG-FE-006: Reporting Recording Playback Test Suite Timeouts & Cascading Re-renders
* **Status:** CONFIRMED BUG
* **Severity:** P1 (Test Suite Failure & Client-Side Re-render Loop)
* **Page / Component:** Reporting Recording Playback & Dashboard
* **File Path & Line Number:** `apps/web/src/app/protected/reporting/reporting-recording-playback.test.tsx`, lines 155–250
* **Expected Behavior:** Clicking "Play" on a recording mounts the `<audio>` element with `src` attribute. Tests should complete in under 500ms.
* **Actual Behavior:** 4 tests fail with `Error: Test timed out in 5000ms` and `TestingLibraryElementError: Unable to find a label with the text of: Call recording audio player`. The DOM output reveals that `ReportingDashboard` remains in an infinite refresh loop (`<svg class="... animate-spin"> Refresh </svg>`).
* **Reproduction Steps:**
  1. Run `npx vitest run src/app/protected/reporting/reporting-recording-playback.test.tsx`.
  2. Observe timeout errors on tests 2, 3, 4, 5.
* **API Dependency:** `GET /workspaces/:id/calls`, `GET /workspaces/:id/recordings/:recId/download`.
* **Root Cause:** In `apps/web/src/app/protected/reporting/page.tsx`, `fetchReporting` updates `campaigns` state, which causes `activeChips` and filter memos to recompute, triggering secondary effects while vitest fake timers or promises are resolving.
* **Suggested Fix:** Remove recursive state updates from `fetchReporting` and decouple dropdown population from the metrics data feed.
* **Regression Test Required:** Run `vitest run reporting-recording-playback.test.tsx` verifying all 5 tests pass cleanly in under 2 seconds.

### BUG-FE-007: Base `apiFetch` Does Not Inject `x-workspace-id` Header by Default
* **Status:** CONFIRMED BUG
* **Severity:** P2 (Multi-Tenant Context Leak Risk)
* **Page / Component:** Core API Client
* **File Path & Line Number:** `apps/web/src/lib/api.ts`, lines 3–29
* **Expected Behavior:** For multi-tenant isolation, the client API layer should attach the active workspace context header (`x-workspace-id`) to every outgoing request.
* **Actual Behavior:** `apiFetch` only attaches `Authorization: Bearer <token>` and `Content-Type: application/json`. Pages must manually format `/workspaces/${workspaceId}/...` into the path string. Any nested endpoint that checks `req.headers['x-workspace-id']` receives `undefined`.
* **Suggested Fix:** Allow `apiFetch` to automatically pull `sessionStorage.getItem('callflow.active_workspace_id')` or pass options with `x-workspace-id`.

### BUG-FE-008: LocalStorage Column Customization Causes State Desync When Schema Evolves
* **Status:** CONFIRMED BUG
* **Severity:** P2 (Client State Inconsistency)
* **Page / Component:** Reporting Dashboard Columns Customizer
* **File Path & Line Number:** `apps/web/src/app/protected/reporting/page.tsx`, lines 392–425
* **Expected Behavior:** When new reporting dimensions (such as `commercial`, `attempts`, or `revenue`) are added to `DEFAULT_COLUMNS`, user browsers with existing `localStorage` keys should merge new columns seamlessly.
* **Actual Behavior:** If a user has a saved configuration in `callflow.reporting.columns.<ws>`, newly introduced columns that are missing from `parsed` are appended without proper default visibility or order, or can cause columns to disappear entirely.
* **Suggested Fix:** Perform an explicit set difference merge on load: any column in `DEFAULT_COLUMNS` not present in `parsed` should be appended with its default visibility and locked properties intact.

### BUG-FE-009: Incomplete Error JSON Body Parsing in `apiFetch`
* **Status:** CONFIRMED BUG
* **Severity:** P2 (User Experience & Error Clarity)
* **Page / Component:** Core API Client
* **File Path & Line Number:** `apps/web/src/lib/api.ts`, lines 21–24
* **Expected Behavior:** When an API error occurs, `apiFetch` should parse JSON error responses (such as NestJS `{ statusCode: 400, message: ["name is required"] }`) and return a human-readable string.
* **Actual Behavior:** `apiFetch` simply reads `res.text()` and throws `new Error(\`API error (${res.status}): ${text}\`)`. Pages often display raw unparsed JSON strings (`API error (400): {"message":["timeout must not be greater than 300"]}`) directly in error banners.
* **Suggested Fix:** Replicate the robust JSON parsing logic already present in `apiDownload` (lines 58–66) inside `apiFetch`.
